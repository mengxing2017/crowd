# ADR 0005：契约包按业务领域组织

## 问题

将 `community/index.ts` 拆成同目录下的类型和客户端文件，只改善文件体积，未建立业务领域边界。目录、推广归因和任务仍通过一个客户端及一个类型入口暴露。

## 决策

- 契约包提供独立 `identity`、`catalog`、`attribution`、`tasks`、`governance` 入口。各领域拥有类型、客户端及相应响应校验。
- `common` 仅包含注入式传输、响应信封、错误及协议适配，不依赖业务领域。
- 每个 `index.ts` 只导出。领域不得依赖 `community`；跨领域快照使用显式类型依赖。
- `community` 降为兼容门面，保留已发布类型和调用方法，通过组合领域客户端及原通用读写适配器兼容旧调用。
- Web 和小程序通过各自 feature 的 `api/index.ts` 接入领域客户端，复用端内 session transport，避免领域间各自保存 token。
- 两端开发与构建均解析本地契约源码，避免新增模块在 pnpm 本地依赖副本中缺失。

领域入口、职责及调用示例见 [API 契约包说明](../../api-contract/README.md)。

## 兼容及限制

保留现有 HTTP 路径、请求体、幂等键、业务错误和服务端权限检查。前端通用提交的结果查询、原键重试及部分旧调用仍经兼容入口处理。

本次不迁移后端聚合状态、数据库和命令路由，也不宣称后端已完成领域解耦。部分前端业务页面仍位于原控制台目录，其 API 依赖已开始按领域迁移。后续后端拆分应单独处理领域状态所有权、事务一致性及历史快照兼容，不能仅移动 Rust 文件。

## 验证范围

`make check-web` 验证契约类型、共享 Rust 序列化样本、独立领域客户端请求和幂等键、响应拒绝、依赖方向及两端类型、lint、构建。此次未改变后端行为，不以这些检查替代业务验收或小程序真机验证。
