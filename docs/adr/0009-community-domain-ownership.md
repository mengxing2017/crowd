# ADR 0009：拆除 community 的混合业务归属

## 范围与验收依据

本次按用户要求重构现有 M01–M12 实现的领域归属，不新增业务策略。上一轮仅拆分应用服务后，用户、收款资料、推广码、规则版本、审计及客服申请仍集中于 `community::domain::State`。验收目标是具体规则和入口具有明确所属模块，生产调用不再依赖 community 兼容命名空间，并保持原协议、历史文档、事务及权限行为。

## 领域与技术模块

| 模块 | 所属实现 |
| --- | --- |
| `identity` | 用户模型、身份与角色／数据范围、资料版本、限制、可信微信登录、管理员密码登录、会话和一次性票据；微信身份端口和凭据适配器 |
| `receipts` | 收款资料新增／停用、脱敏与本人查看、敏感查看审计、微信收款文件用途及归属校验 |
| `promotion` | 推广码模型、唯一归属、创建／换发、目标可用性、解析与二维码、初始推广码生成任务 |
| `governance` | 平台规则草稿／发布／停用、规则权限、旧产品任务规则内容校验、服务协议与隐私说明查询 |
| `audit` | 成功／失败审计记录、发布规则版本关联、按权限和对象范围查询 |
| `support` | 收款纠错、注销、合并的待核查申请；保持原有依赖待核查状态 |
| `catalog` | 既有产品、分类、生命周期和访问归因规则；产品图片读取适配器 |
| `tasks` | 既有定价、模板、执行、证据和审核；参与资格 HTTP 入口、证据上传约束／附件关联、未使用证据删除适配器 |
| `files` | 真实图片格式／资源限制、用途与所有者访问、上传和私有文件读取；任务证据业务检查委托任务领域 |
| `shared` | 稳定错误及结果类型、基础字段／版本校验、整数分金额显示，不保存业务规则或接口客户端 |
| `platform` | 既有通用读写协议的分派、跨领域事务／幂等／失败恢复、依赖组装、共享状态存储及兼容门面 |
| `community` | 仅重新导出旧 `domain`、`north`、`south` 命名空间，不再拥有实现文件 |

各领域拥有自己的 `domain/` 和／或 `north/`、`south/` 实现。领域规则不引用 Axum 或 SQLx；SQL 适配器迁入实际所属模块，通用 PostgreSQL 事务和历史状态存储保留在 `platform/south/adapter/postgres/`。现阶段这些适配器继续扩展共享 `Repository`，用于复用同一事务和原 Rust 方法签名；这不是独立领域仓储端口已经全部建成的声明。

各领域 remote 入口自行组装路由，platform 仅合并路由与保留旧通配协议。具体应用服务从 `ApplicationServices` 注入，旧 `Service` 方法仍只委托。本轮后端迁移本身不改变 HTTP 签名；客户端方法归属的后续调整另见 ADR 0010。

后续契约与前端同步见 [ADR 0010](0010-contract-frontend-domain-ownership.md)：原客户端中的混合方法已迁至独立入口，两端调用同步调整，原 HTTP 协议与 community 兼容门面保留。

## 兼容与一致性

- 保留全部 `/api/v1/community/*` 路径及原请求／响应字段、业务错误码。URL 前缀不再代表后端领域所有权，不需要同步发布新客户端。
- `State` 移至 `platform/domain/state.rs`，作为现有跨领域事务的兼容状态文档。`User` 与 `Code` 类型分别归身份与推广领域；原有 `users`、`rules`、`codes`、`cases`、`audit`、`idempotency`、`tasks`、`catalog` 序列化键保持不变，旧记录无需数据迁移。
- 具体用户、推广和审计行为在其所属领域实现；通用查询和命令按所属领域分派，字段白名单和操作授权由各自领域维护。共享 State 上的兼容方法仍存在，避免本次同时改变全局锁及原子提交边界。
- 不新增独立提交：资料版本、推广历史、任务、审计和有效幂等结果仍使用原事务；命令失败保留原状态回滚及失败审计。权限仍在返回有效幂等结果前检查。
- 保留重复停用收款资料和已存在推广码的原无变化返回行为；不额外增加审计或递增版本。收款原记录继续追加状态事件，不覆盖旧快照。
- 不新增付款、查单、自动结算、金额阈值或审核策略。审计迁移不改变记录保留和查看范围。

本次完成领域实现及入口归属拆分。持久化仍是共享状态文档，部分原始字段仍使用 JSON；尚未将其改造成多个独立聚合、数据库表或独立仓储端口。后续隔离存储须另行设计跨领域一致性及历史兼容，不将本次文件和归属拆分描述为所有领域完全解耦。

## 验证

```bash
devbox run -- make check-backend
devbox run -- make test-business
```

新增领域边界检查防止生产代码重新依赖 community 兼容命名空间，禁止领域引入 HTTP／SQL 实现，检查共享存储及分派器不接收具体业务实现。应用服务单一入口和 `mod.rs` 导出约束继续执行。

新增历史文档序列化／旧 Rust 命名空间兼容测试、重复操作审计和收款历史回归、规则权限与审计数据范围回归。既有领域与 HTTP 测试、独立嵌入式 PostgreSQL 集成测试继续覆盖并发、幂等、文件授权、任务审核和批量失败恢复。

2026-10-28 实际验证：Devbox / Rust 1.97.1 下 `make check-backend` 的格式检查、编译、Clippy 和 55 项测试全部通过，模块入口检查覆盖 83 个 `mod.rs`；`make test-business` 在隔离的嵌入式 PostgreSQL 17 上通过 1 项数据库集成测试，未连接外部数据库。`git diff --check` 通过。此次未改动前端或契约包，未执行前端构建和微信真机验证；自动化测试不代替业务验收或官方到账验证。
